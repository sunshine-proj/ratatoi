What's set up

App: Next.js 16.4 (App Router), React 19, strict TypeScript, Tailwind 4 and ESLint, using npm with the lockfile included. The home page is a placeholder.
Scripts: dev, build, start, lint, typecheck, test, test:watch, test:e2e, and check, which runs lint, typecheck, unit tests and build together.
Tests: Vitest and React Testing Library for unit tests in tests/unit/, and Playwright in tests/e2e/.
Validation: lib/validation/ has shared Zod rules for non-negative amounts, servings above zero, whole minutes, YYYY-MM-DD dates, slugs and required text. Per-feature schemas will build on these.
Text: all UI strings live in one typed English file, lib/i18n/messages/en.ts. Adding Lithuanian means adding an lt.ts file, and a missing string becomes a type error.
Folders and config: the folder layout from the README, .env.example with no required variables (Supabase placeholders are commented out), .nvmrc set to Node 24, and a CI workflow in .github/workflows/ci.yml.
Docs: README updated with project status, stack, scripts, structure and how to add a language; Phase 0 tasks ticked in ROADMAP.md.
Decisions worth knowing

End-to-end tests run on port 3210 and never connect to a server that's already running. On your machine, ports 3000 and 3100 are both taken by other apps (one of them a Grafana login page), and the first test run quietly tested Grafana instead of this app. If the port is busy, the run now fails with a clear error. You can change the port with E2E_PORT.
next dev adds its own rules block to AGENTS.md if the block isn't there. I added it myself, so the file won't keep changing unexpectedly.
I turned on a stricter TypeScript setting (noUncheckedIndexedAccess). It catches missing array and object entries, which matters for the nutrition and shopping-list maths, and it's easier to adopt now than later.
I upgraded @types/node to version 24 because the test tooling required it. I left out the separate path-alias plugin because Vite 8 handles that itself.
I kept Next's default settings and the Geist font. Fonts download from Google at build time, so builds need network access. Phase 1 will settle the fonts and design.
There's no locale-based routing. Language is planned as a user setting, which fits a guest-first app.

Phase 2 is done and every roadmap item is ticked. Lint, typecheck, all 123 unit and component tests, the build and the end-to-end tests pass. Nothing is committed.

What users can do now

Set up their plan at /onboarding in 5 steps:

Choose a goal.
Optionally estimate targets, or skip.
Set calorie and protein targets, with optional carbohydrate and fat.
Choose food preferences: eating pattern, the 14 EU-declared allergens, other ingredients to avoid, cooking confidence, budget, and meals and snacks per day.
Check a summary with an Edit link per section, then save.
Running it again fills in their earlier answers.

Change targets at /settings/goals. They can re-estimate from a dialog, and clearing targets asks for confirmation first. Change food preferences at /settings/preferences.

See their targets on Today, or a "Set up your plan" prompt if they haven't set any.

How the estimate works (your "Estimate now" choice)

Formula: calories use Mifflin-St Jeor. Fat loss takes off a moderate 15%, muscle gain adds 10%. Protein is 1.8 or 1.4 g per kg of body weight.
Limits: it never suggests below 1,200 kcal, protein is capped at 35% of calories, and it's for adults only.
"Prefer not to say" for sex uses the midpoint of the formula's two versions.
The full working is always shown. The user edits the numbers before anything is saved, and a disclaimer appears wherever targets are set.
Age, sex, height, weight and activity are never saved. Tests check this.
Decisions worth knowing

Saving: settings are stored in the browser under one key and checked against the schema on every read. If the saved data is damaged, the app explains and offers a reset; if storage is blocked or full, it shows an error and changes nothing. The app tells users that anyone using the same browser can see this data.
Forms: hand-written rather than React Hook Form. "72,5", "1,900" and "1 900" are all accepted. Errors are specific (for example, "Enter a value from 800 to 6,000"), and the first wrong field gets focus.
Gentle notices: targets below 1,200 kcal, or macros that add up to more than the calorie target, get a neutral note. They don't block saving.
Bugs found and fixed along the way

Next 16 keeps up to three recent pages alive in the background, along with their form state. That caused two problems:
Going back to onboarding after finishing reopened the old summary step. The wizard now resets after a successful save.
The Goals form could show old targets after they were changed in onboarding, and pressing Save would have overwritten the new ones. The forms now reload whenever the saved data changes.
Toasts covered the bottom action buttons on phones, so I moved them to the top of the screen.
I removed a redundant "Estimate added" toast from the wizard.

Phase 3 is done except recipe photography, and that roadmap item is still unchecked. Lint, typecheck, the 168 unit tests, the build and the end-to-end tests all pass. Nothing is committed.

What users can do now

Browse /recipes: 25 original recipes covering breakfast, lunch, dinner and snacks, with vegan, vegetarian, fish and meat options and quick and batch-cook dishes.
Search by recipe name or ingredient, including other names: "shrimp" finds prawns, "zucchini" finds courgettes.
Filter by meal, minimum protein, maximum calories, time, diet, allergens and ingredients to leave out. On phones the filters open in a bottom sheet; on desktop they sit in a sidebar.
Sort by most protein, fewest calories, quickest, or name.
Active filters show as chips you can remove one by one. If nothing matches, the page explains why and offers a reset.
Saved preferences are applied by default. A note above the results says what's being hidden ("Hiding: Fish") and has a switch to turn it off.
Recipe pages show:
nutrition per serving, labelled "Estimated"
ingredients with metric amounts, such as "2 cloves" and "½ Onion"
numbered steps
allergens, with a note to check product labels
storage notes
how each label is decided, and where the recipe and nutrition data come from
Find snacks at /snacks with one-tap presets (up to 150, 200 or 250 kcal, with at least 15, 20 or 25 g protein). They're never applied automatically, and the numbers stay editable.
Decisions worth knowing

Nutrition is calculated, not typed in. Each recipe's per-serving values come from an ingredient table and are stored in the recipe, and a test fails if they ever drift from the calculation. Allergens and vegan/vegetarian suitability are also derived from the ingredients, so they can't contradict the ingredient list.

Every label has a stated rule:

"High protein" means at least 20% of energy comes from protein (the EU condition for the claim).
"Under 200 kcal" (snacks) and "Under 450 kcal" (meals) are per serving.
"Quick" means 15 minutes or less in total.
Nothing is called "low calorie". As a result, the chickpea, tofu and spinach curry (19% protein) doesn't get the "High protein" label.

Unknown recipe URLs return a real 404. With Next 16's Cache Components, the page starts sending before it can tell the recipe is missing, so it would otherwise return a 200 status. A small proxy.ts checks the recipe name first, as the Next docs recommend.

Issues found and fixed along the way

Counted ingredients read "1 Lemons" and "½ Onions". They now use singular names.
The hidden results heading reused the "Search recipes" text, so screen readers heard the results area named like the search box. It now has its own "Results" heading.

Phase 4 is finished and every roadmap item is ticked. Lint, typecheck, all 201 unit tests, the build and the 81 end-to-end tests pass. Nothing is committed. As you asked, I paused at 12:31 and resumed at 13:30.

What users can do now

Plan a week at /planner.
Move between weeks, or jump back with "This week".
A seven-day tab strip fits a 320 px phone without sideways scrolling. Today is marked with a ring, and dots show how many meals are planned.
Each day has breakfast, lunch and dinner slots plus any number of snacks. Empty slots show "Nothing planned" with an add button, and can stay empty.
Add meals: recipes from a searchable sheet (with saved food preferences applied), or your own meal with typed-in nutrition. Your own meals are always labelled "Your own meal… not a verified recipe".
Edit meals:
change servings in quarter steps, and the day's totals update straight away
swap a meal, with each option showing how the day changes (for example "+134 kcal · −8 g protein")
duplicate to another day or meal, or move up and down within a slot
remove, with Undo (swaps can be undone too)
clear a day or the whole week, after confirming
Add to plan from a recipe: recipe pages have an "Add to plan" button and cards have a "+". You pick the day, meal and servings, and a toast offers View plan, which opens that day.
Your plan is saved in the browser. It survives refresh and navigation, and the selected day is in the URL.
Decisions worth knowing

Dates are stored as plain calendar dates with no time zone, meaning "your Thursday". The maths can't be thrown off by daylight-saving changes, and a test covers the EU clock change. Weeks start on Monday, and dates display day-first ("Thu 26 Nov").
Unknown nutrition is never counted as zero. If a planned recipe no longer exists, the day's total says "Plus 1 meal without nutrition information".
The plan is saved separately from your settings. If the saved plan is ever damaged, the planner says so, won't overwrite it without asking, and offers a reset that keeps your goals and preferences.
The day and meal totals Phase 5 needs are already built and tested. The roadmap notes which parts are done.
Bugs found and fixed along the way

Without an item name, the servings buttons were labelled "More servings of servings". They now read "More servings" and "Fewer servings".
The recipe-card focus ring would have lit up the whole card whenever its new "+" button had focus. It now appears only when the recipe link is focused.
Checks I ran

npm run test:e2e: 81 passed, 9 skipped on purpose (desktop-only checks). They run with the clock fixed to Thu 26 Nov 2026 and cover adding from a recipe card through to "View plan" and a reload, planning, swapping and clearing a week, week navigation, and 320 px phone width.
I also checked screenshots of the planner and the swap sheet.
