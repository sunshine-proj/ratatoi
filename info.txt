Decisions worth knowing

End-to-end tests run on port 3210 and never connect to a server that's already running. On your machine, ports 3000 and 3100 are both taken by other apps (one of them a Grafana login page), and the first test run quietly tested Grafana instead of this app. If the port is busy, the run now fails with a clear error. You can change the port with E2E_PORT.
next dev adds its own rules block to AGENTS.md if the block isn't there. I added it myself, so the file won't keep changing unexpectedly.
I turned on a stricter TypeScript setting (noUncheckedIndexedAccess). It catches missing array and object entries, which matters for the nutrition and shopping-list maths, and it's easier to adopt now than later.
I upgraded @types/node to version 24 because the test tooling required it. I left out the separate path-alias plugin because Vite 8 handles that itself.
I kept Next's default settings and the Geist font. Fonts download from Google at build time, so builds need network access. Phase 1 will settle the fonts and design.
There's no locale-based routing. Language is planned as a user setting, which fits a guest-first app.

What users can do now

Set up their plan at /onboarding in 5 steps:

How the estimate works (your "Estimate now" choice)

Formula: calories use Mifflin-St Jeor. Fat loss takes off a moderate 15%, muscle gain adds 10%. Protein is 1.8 or 1.4 g per kg of body weight.
Limits: it never suggests below 1,200 kcal, protein is capped at 35% of calories, and it's for adults only.
"Prefer not to say" for sex uses the midpoint of the formula's two versions.
The full working is always shown. The user edits the numbers before anything is saved, and a disclaimer appears wherever targets are set.
Age, sex, height, weight and activity are never saved. Tests check this.
Decisions worth knowing

Saving: settings are stored in the browser under one key and checked against the schema on every read. If the saved data is damaged, the app explains and offers a reset; if storage is blocked or full, it shows an error and changes nothing. The app tells users that anyone using the same browser can see this data.
Forms: hand-written rather than React Hook Form. "72,5", "1,900" and "1 900" are all accepted. Errors are specific (for example, "Enter a value from 800 to 6,000"), and the first wrong field gets focus.
Gentle notices: targets below 1,200 kcal, or macros that add up to more than the calorie target, get a neutral note. They don't block saving.

Toasts covered the bottom action buttons on phones, so I moved them to the top of the screen.
I removed a redundant "Estimate added" toast from the wizard.

Decisions worth knowing

Nutrition is calculated, not typed in. Each recipe's per-serving values come from an ingredient table and are stored in the recipe, and a test fails if they ever drift from the calculation. Allergens and vegan/vegetarian suitability are also derived from the ingredients, so they can't contradict the ingredient list.

Every label has a stated rule:

"High protein" means at least 20% of energy comes from protein (the EU condition for the claim).
"Under 200 kcal" (snacks) and "Under 450 kcal" (meals) are per serving.
"Quick" means 15 minutes or less in total.
Nothing is called "low calorie". As a result, the chickpea, tofu and spinach curry (19% protein) doesn't get the "High protein" label.

Unknown recipe URLs return a real 404. With Next 16's Cache Components, the page starts sending before it can tell the recipe is missing, so it would otherwise return a 200 status. A small proxy.ts checks the recipe name first, as the Next docs recommend.

How progress is worded and calculated

Neutral wording: "200 kcal remaining", "0 g remaining", "150 kcal above target". There's no red, no warning colours and no "over budget" language. Each panel carries the PRD line "Planning figures, not a judgement or medical assessment."
Numbers always add up. Values are kept precise, and planned is rounded once for display, with remaining worked out from that rounded figure. So 1,699.5 kcal shows as 1,700 planned and 200 remaining, never 1,700 and 201.
Unknown stays unknown. If any meal lacks carbohydrate information, that row says "Unknown" rather than showing a partial number.
The weekly average covers only the selected Monday to Sunday and is averaged over days with meals planned. The summary says so, so an unplanned weekend doesn't halve the figure.
Screen readers: the bars are decorative, because the text beside them carries the meaning. Day totals are announced only after changes settle, so tapping "+" four times gives one announcement, not four.

What users can do now (/shopping-list)

Empty plan: a "Go to meal plan" link. Once a list exists, it shows first, which is better in a shop.
How amounts are combined

Scaling: planned servings ÷ the recipe's servings.
Combining: by ingredient and unit family. Spoons and millilitres combine, because a spoon is a fixed volume; spice-sized amounts stay in teaspoons. Grams and millilitres are never converted into each other, because there's no reliable per-ingredient density data, so they stay on separate lines.
Display: rounding is only for display. Large amounts show as kg or l, pieces show in quarters, and a small amount never displays as 0.
Not guessed: custom meals have no ingredient list, so the page says how many were left out rather than estimating.
Saved separately from the plan and settings. A damaged list is never overwritten without asking, and resetting it leaves everything else alone.
Bugs found and fixed along the way

A half-typed custom date crashed the page. It now shows a validation message instead.
